## 1. 规划结论

后续开发收缩为“使用本地商品数据跑通搜索推荐业务”的单实例 MVP，不再以正式上线门禁为当前目标。

除独立测试、上线和运维工作外，本规划按 4 个增量推进：

1. M1：`processed` 数据源收口；
2. M2：千问 Embedding 正式接入；
3. M3：搜索推荐主链路收口；
4. M4：受控白名单 `web_search` 接入。

当前项目已有 BM25、TF-IDF、RRF、Fast/Deep Path、Agent 编排、Embedding/VectorIndex 端口、真实 Qwen3 Embedding 权重和 5 万商品 SQLite 向量索引。M1 与 M2 已完成；后续重点是把经过验证的 Qwen Challenger 切入默认混合召回，再完成受控外部搜索闭环，不再扩展过细的业务能力。

当前里程碑状态：

| 增量 | 状态 | 当前结论 |
|---|---|---|
| M1 processed 数据源收口 | 已完成 | 5 万商品、默认路径、字段顺序、数据质量和快照版本已统一 |
| M2 Qwen Embedding 与向量索引 | 已完成 | 真实权重、SQLite 索引、全量/增量构建、版本校验和降级均已验证 |
| M3 搜索推荐主链路收口 | 进行中 | Active 正式融合与降级已完成；等待 processed 固定查询集质量门禁 |
| M4 白名单 web_search | 未开始 | 等待 M3 默认本地链路稳定后接入 |

## 2. MVP 范围

### 2.1 本阶段必须完成

- 单实例本地运行；
- 默认读取 `data/processed` 下的商品数据；
- 支持关键词搜索和语义搜索；
- 支持关键词召回、向量召回和 RRF 融合；
- 支持分类、价格、库存等基础过滤；
- 返回可解释的商品推荐结果和数据来源；
- Embedding 不可用时能够降级到 BM25/TF-IDF；
- 本地证据不足时能够调用受控 `web_search`；
- 外部搜索只能访问明确允许的国内信息来源网站。

### 2.2 本阶段不做

- 正式业务数据接入和实时业务数据同步；
- 多实例部署、共享状态、分布式任务和水平扩展；
- Milvus、Elasticsearch 向量检索或其他生产级 ANN 集群；
- 复杂用户画像、行为学习和精细个性化；
- 完整约束生命周期、复杂单位换算和类目属性矩阵；
- LTR 训练、生成式召回和高级模型实验；
- OpenTelemetry、监控 Dashboard、生产告警和 Runbook；
- 生产鉴权、限流、容灾和灾备；
- 生产级 Shadow、Canary、A/B、上线和回滚流程；本地 Challenger 对照审计继续保留。

上述能力不删除现有代码，但不再作为当前 MVP 的阻塞项，也不安排新的扩展开发。

## 3. 数据基线

### 3.1 数据来源

MVP 固定使用以下数据：

```text
data/processed/kuaisearch-electronics/items.jsonl
data/processed/kuaisearch-electronics/report.json
```

当前 `items.jsonl` 固定包含 50,000 条电子商品，已删除手机壳商品类别，并按商品类型确定性补齐本地测试字段。每条商品已经包含商品标识、标题、品牌、卖家、分类、价格、库存、销量、评分、评价数和使用场景等字段，足以支持本阶段的搜索推荐闭环。

当前 Catalog 快照：

```text
items: 50000
snapshot_sha256: e1063931609d4bb40a7121499344e82e06ab92a043e050f9997c712357f7abfb
```

### 3.2 数据使用原则

- `processed` 数据是当前唯一默认业务数据源；
- `data/sample` 只用于最小示例，不得在正常启动时静默替代 `processed` 数据；
- 不再等待正式业务字段或正式数据平台；
- 合成字段仅用于本地功能演示，不描述为真实业务事实；
- 数据导入、索引构建和增量更新必须幂等；
- 索引元数据必须记录数据快照哈希、商品数量、模型版本、向量维度和构建时间。

## 4. Embedding 模型选型

### 4.1 默认型号

MVP 默认采用：

```text
Qwen/Qwen3-Embedding-0.6B
```

官方模型卡显示，该模型为 0.6B 参数，支持 100 多种语言、32K 上下文和最高 1024 维向量，并支持 32～1024 维可配置输出以及查询指令。对于当前 5 万条商品和单实例本地运行，它在资源占用与中文检索能力之间更合适。

参考资料：

- [Qwen3-Embedding-0.6B 官方模型卡](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)
- [Qwen3 Embedding 官方代码仓库](https://github.com/QwenLM/Qwen3-Embedding)
- [Qwen3 Embedding 论文](https://arxiv.org/abs/2506.05176)

### 4.2 首版模型配置

```text
model_id: Qwen/Qwen3-Embedding-0.6B
revision: main
embedding_dimension: 1024
document_instruction: 不添加
query_instruction: 为给定的商品搜索查询，检索满足用户需求的商品
device: auto（当前本机解析为 cuda:0）
batch_size: 16
model_cache: .runtime/model-cache
vector_index_path: .runtime/qwen3-embedding-0.6b-vectors.sqlite3
vector_index: SQLite + sqlite-vec 版本化精确向量索引（VectorIndex 端口可替换）
```

查询使用任务指令，商品文档不添加指令。模型、缓存目录、设备和批大小必须通过配置或环境变量控制，不得硬编码到业务逻辑。

### 4.3 暂不采用的型号

- `Qwen3-Embedding-4B`：保留为未来资源允许时的效果对照型号，不作为 MVP 默认依赖；
- `Qwen3-Embedding-8B`：资源占用明显高于当前 MVP 需要，本阶段不接入；
- Qwen Reranker：当前已有 Cross-Encoder Challenger 接口，但重排模型不是跑通业务的必要条件，本阶段默认关闭。

## 5. 目标运行链路

### 5.1 本地搜索推荐

```text
用户请求
  → 查询理解与基础约束提取
  → BM25 关键词召回
  → Qwen Embedding 向量召回
  → RRF 融合与去重
  → 分类/价格/库存基础过滤
  → 商品详情与证据补全
  → 推荐结果和推荐理由
```

### 5.2 外部信息补充

```text
本地搜索结果不足
  → Deep Path 判断是否需要外部信息
  → web_search Provider
  → 查询前站点限制
  → 返回结果域名二次校验
  → 结构化 WebSearchResult
  → 与本地结果/证据合并
```

外部搜索不得替代本地商品搜索。只有本地证据不足、用户明确要求外部信息或查询需要跨站比较时，才允许进入 `web_search`。

## 8. 增量 M3：搜索推荐主链路收口

**状态：进行中（Active 主链路代码已完成，首轮质量门禁未通过）。** 默认主路径已经具备 BM25、
TF-IDF、并行工具调用、RRF、基础约束、Catalog/ACL 复核、详情补全、推荐理由、Receipt 和有界
降级。`off/challenger/active` 三态、BM25+Qwen 正式融合、Active 成功路径移除 TF-IDF 重复扫描、
失败/空结果 TF-IDF 降级以及候选/SSE/Receipt 来源标记均已完成。当前本地默认仍保持 Challenger，
processed 首版 13 条固定查询集已经完成；Active 暖态 P95 通过，但 Recall/MRR/NDCG 均退化，
因此本地默认继续保持 Challenger。独立开发集上的 0.25～2.0 加权 RRF 扫描仍选择等权 1.0，
简单权重调整不能修复质量；下一步转向类别感知召回，再用留出集复验。

### 8.1 目标

让 BM25 和 Qwen Embedding 混合召回成为默认搜索推荐链路，完成从用户查询到可解释商品结果的端到端闭环。

### 8.2 开发任务

4. 统一 Fast Path 和 Deep Path 的 Catalog 快照、索引版本、候选来源和结果契约；
5. 保留分类、价格、库存、租户、状态和 ACL 等确定性复核；
6. 在候选、SSE 和 Receipt 中标记关键词、Qwen、融合或降级来源；
7. 模型调用失败、索引缺失、版本不匹配或结果为空时有界降级到 TF-IDF/BM25；
8. 增加固定查询集对照，比较 BM25+TF-IDF 与 BM25+Qwen 的 Recall/NDCG、零结果和暖态延迟；
9. 评估启动后受控模型预热，避免约 11.9 秒模型冷加载落到首个用户请求；

## 9. 增量 M4：受控白名单 web_search

**状态：未开始。** 当前工具注册表已有本地 Catalog、语义、行为和商品详情能力，尚未定义
`WebSearchProvider/WebSearchResult`、统一 URL 白名单策略或外部证据融合。M4 不阻塞 M3，
但在本地 Active 主链路稳定前不接入默认执行流。

### 9.1 目标

完成第五类只读工具 `web_search`，只允许访问指定的国内购物和信息来源网站，并将外部结果作为受控证据接入 Deep Path。

### 9.2 域名白名单

只允许以下根域名及其合法子域名：

```text
taobao.com
jd.com
tmall.com
baidu.com
xiaohongshu.com
douyin.com
meituan.com
```

除上述域名外，其他网站不得请求、抓取、返回或作为推荐证据。

### 9.3 白名单判定规则

- 仅允许 `https` 协议；
- Host 必须等于白名单根域名，或者以 `.` 加根域名结尾；
- 禁止使用字符串包含、模糊匹配或仅检查 URL 文本；
- URL 标准化后再校验 Host、端口和用户信息；
- 每次重定向都必须重新校验目标地址；
- 搜索 Provider 返回结果后必须再次过滤；
- 外部结果中的 URL、摘要和页面内容均视为不可信数据；
- 短链接只有在解析后的最终地址仍属于白名单时才允许使用。

例如，`item.jd.com` 可以通过，`jd.com.example.org` 和 `fake-jd.com` 必须拒绝。

### 9.4 百度的处理边界

如果百度仅作为搜索 Provider，其返回结果不能因为来自百度搜索接口而自动放行。最终结果 URL 仍必须属于七个白名单根域名。

如果将百度页面本身作为信息来源，则只允许 `baidu.com` 及其合法子域名，不允许通过百度跳转链接访问任意外站。

### 9.5 开发任务

1. 定义 `WebSearchProvider` 端口和标准 `WebSearchResult`；
2. 增加统一的域名白名单策略组件；
3. 在发送查询前增加站点限制；
4. 对 Provider 返回的每条结果执行协议和域名复核；
5. 将外部标题、摘要、来源 URL、来源站点和检索时间写入证据；
6. 只允许 Deep Path 在本地结果不足时调用；
7. 增加 Feature Flag、调用次数预算、超时和失败降级；
8. Provider 无凭据或不可用时回退到本地搜索，不影响基础业务；
9. 不建设通用网页爬虫，不绕过登录、验证码或网站访问控制。

### 9.6 完成标准

- `web_search` 能通过统一 Tool 接口被 Agent 调用；
- 白名单站点结果能够返回并生成引用；
- 任意非白名单 URL 均在网络访问前或结果进入主链路前被拒绝；
- 外部搜索失败不会导致整个搜索推荐请求失败；
- Receipt 能记录是否调用外部搜索、Provider、来源域名和降级原因。

### 9.7 外部依赖

需要至少一个可配置的 Web Search Provider 及对应凭据。Provider 的选择不应进入业务核心，后续可在不修改 Agent 主链路的情况下替换适配器。

### 9.8 预估工作量

1.5～2 个开发日，不包含外部服务申请和审核时间。

## 12. 开发约定

- 新增 Python 模块、类、函数和关键分支必须添加清晰的中文注释；
- 注释说明设计意图、输入输出和降级原因，避免逐行翻译代码；
- 配置项必须集中管理，不在业务代码中硬编码模型路径、数据路径和密钥；
- 优先扩展现有端口和适配器，不在 Agent 节点中直接依赖具体模型或 Provider；
- 每个增量完成后同步更新本文档的状态和下一步；
- 自动化测试不作为独立功能增量，但新增主链路必须保留必要的自检和回归验证；
- 项目暂不上线，不以生产部署门禁阻塞当前 MVP 完成。
