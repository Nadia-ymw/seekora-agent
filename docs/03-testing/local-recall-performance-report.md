# 本地并行召回与 SQLite 向量索引性能报告

## 1. 结论摘要

2026-08-22 在 5 万商品目录上完成一次暖态本机测量。当前双路召回墙钟耗时为 P50 1,393.4 ms、P95 1,831.6 ms，`vector_search` 与总墙钟几乎相同，说明向量分支是当前关键路径。

测试中观察到的相对旧 JSON 索引提速是可信的，主要原因不是“SQLite 是向量数据库”这一标签，而是查询实现从 Python 逐元素遍历 50,000 × 1,024（每次查询约 5,120 万个维度乘加）迁移到了 `sqlite-vec` 的原生 C 精确 KNN，同时避免了巨大 JSON 的解析、Python 浮点对象和全量向量常驻。

并行编排确实让 BM25 与向量工具发生时间重叠，但目前不能把调用耗时之和与墙钟差值直接当作严格加速比。BM25 和 TF-IDF 都是 Python CPU 全表扫描，并行时会争用 CPU/GIL；孤立组件耗时的简单总和与并行墙钟接近，说明相当一部分理论并发收益被资源竞争抵消。当前结果属于本地 Challenger 性能证据，不代表生产 SLA，也不足以通过 Phase 1 正式性能门禁。

测试期间未固定 CPU 频率，也未关闭桌面后台进程。以下 P95 是小样本工程观测值，只用于定位瓶颈，不用于容量承诺。

## 3. 测量方法

1. 使用已经完成同步并通过模型、维度、Catalog 快照和商品数校验的 SQLite 索引；
2. 模型和检索各预热一次后测量暖态数据；模型首次加载单独记录为冷态样本；
3. BM25、TF-IDF 各独立执行 20 次，取 Top 30；
4. Qwen 查询编码执行 20 次，SQLite KNN 执行 50 次，取 Top 50；
5. 使用真实 `RecallOrchestrator → LangChainToolRegistry → ToolNode` 链路执行 12 次双路召回；测试上下文没有 `user_id`，因此行为召回按设计跳过；
6. 并行结果同时记录墙钟耗时和每个工具内部耗时。工具耗时发生重叠，其总和仅作为重叠程度指标，不能视为无竞争的串行基线。

## 4. 测量结果

### 4.1 索引构建与增量同步

| 指标 | 结果 |
|---|---:|
| 首次构建商品数 | 50,000 |
| 首次构建成功/失败 | 50,000 / 0 |
| 首次构建耗时 | 456.996 s |
| Embedding 批大小 | 16 |
| 重复同步重算数 | 0 |
| 重复同步未变化数 | 50,000 |
| 重复同步耗时 | 0.758 s |

重复同步无需加载模型或重新生成向量，说明内容哈希和批事务增量路径工作正常。

### 4.2 孤立组件暖态延迟

| 组件 | 样本数 | P50 | P95 | 说明 |
|---|---:|---:|---:|---|
| BM25 Top 30 | 20 | 759.2 ms | 864.4 ms | Python 5 万商品扫描 |
| TF-IDF Top 30 | 20 | 427.7 ms | 510.8 ms | Python 稀疏向量扫描 |
| Qwen Query Embedding | 20 | 43.7 ms | 57.7 ms | 模型已加载，CUDA |
| sqlite-vec KNN Top 50 | 50 | 156.2 ms | 388.7 ms | 5 万 × 1,024 精确余弦扫描 |

Qwen 模型首次加载单样本为 11,854.2 ms。它不应混入暖态 P50，但会显著影响进程启动后的第一次 Challenger 查询。

### 4.3 真实双路并行召回

| 指标 | 样本数 | P50 | P95 |
|---|---:|---:|---:|
| 并行召回墙钟 | 12 | 1,393.4 ms | 1,831.6 ms |
| `catalog_search` 工具耗时 | 12 | 674.0 ms | 1,099.0 ms |
| `vector_search`（TF-IDF + Qwen Challenger）工具耗时 | 12 | 1,392.0 ms | 1,830.0 ms |
| 同一次请求中两工具耗时之和 | 12 | 2,136.5 ms | 2,929.0 ms |

墙钟相对“并发工具耗时之和”少 34.8%（P50）和 37.5%（P95），证明两个工具存在明显时间重叠。但这个百分比不是严格的串行加速比：并发时两个 Python 检索会相互争用资源，导致每个工具的观测耗时膨胀。

孤立组件 P50 的简单串行和约为：

```text
BM25 759.2
+ TF-IDF 427.7
+ Query Embedding 43.7
+ SQLite KNN 156.2
= 1,386.8 ms
```

它与并行墙钟 P50 1,393.4 ms 接近。因此现阶段更准确的表述是：编排实现了 I/O/GPU/C 扩展与工具调用的重叠，但 BM25/TF-IDF 的 Python CPU/GIL 竞争消耗了大部分可见并发红利。

## 5. 为什么新索引明显更快

### 5.1 移除了 Python 内层余弦循环

旧 `VersionedVectorIndex.search()` 需要在 Python 中对每个商品执行 1,024 维 `zip + multiply + sum`，单次查询约处理 5,120 万个维度对。新 `SQLiteVectorIndex.search()` 只序列化一个查询向量并提交 KNN SQL，向量扫描和距离计算在 `sqlite-vec` 原生扩展中完成。

复杂度仍然是精确扫描的 O(N × D)，并没有变成 ANN；提升来自更紧凑的 float32 存储、原生循环、更少的 Python 对象分配和更好的数据局部性。

### 5.2 避免巨大 JSON 的启动成本

旧方案必须读取完整 JSON、解析每个浮点数并创建嵌套 Python `list/float` 对象。SQLite 只加载元数据和连接，向量页由 SQLite 按需读取并由操作系统缓存。由此降低了启动解析时间和 Python 堆内存压力。

### 5.3 SQLite 缩短了并行关键路径

并行召回的墙钟下界接近最慢分支，而不是所有分支之和。当前 `vector_search` 是最慢分支，因此 SQLite KNN 缩短向量分支会直接缩短整体召回墙钟；BM25 再快也无法越过这一关键路径约束。

## 6. 当前瓶颈和边界

1. `vector_search` 内部先执行 TF-IDF 主路径，再执行 Qwen Challenger，两者当前是串行关系；
2. BM25 和 TF-IDF 都遍历 5 万商品并执行 Python 计算，并发时存在 CPU/GIL 竞争；
3. `sqlite-vec/vec0` 当前仍是精确 KNN，目录继续扩大后延迟会近似线性增长；
4. 模型保持延迟加载，进程首次 Challenger 查询可能承担约 11.9 秒冷启动；
5. SQLite 适合本地单实例，当前同一索引连接通过锁保护，并发查询会在连接级串行；
6. 本次没有保留旧 5 万条 JSON 索引，因此没有同机、同查询、同进程的旧/新 A/B 数字，不能给出严谨的“比旧版快 X 倍”；
7. 样本数较小，未覆盖登录用户的第三路行为召回、Deep Path 多查询、并发 QPS、SSE 首事件、内存峰值和长时间稳定性。

## 7. 后续优化优先级

### P0：补齐可重复性能门禁

- 固定 50～100 条查询集，分别记录冷启动、暖态 TP50/TP95/TP99；
- 从 Receipt 汇总各工具、Embedding Challenger 和端到端耗时，而不是依赖单次人工观察；
- 增加 1、5、10、25 并发的阶梯测试，记录 GPU、CPU、内存、SQLite 锁等待和错误率；
- 将数据快照、模型版本、索引版本、设备和配置写入每份结果。

### P1：减少重复的 Python 全表扫描

- 在 M3 质量门禁通过后，评估让 Qwen Embedding 成为正式语义召回，避免每次在同一 `vector_search` 中同时执行 TF-IDF 全表扫描和 Shadow 向量扫描；
- Challenger 期间可评估 TF-IDF 与 Qwen 子任务并行，但必须控制线程、CPU 和 GPU 竞争；
- 将 BM25/TF-IDF 替换为原生实现、倒排索引或进程隔离，单纯增加线程不能消除 Python GIL 成本。

### P2：控制冷启动和规模增长

- 服务启动后执行一次受控模型预热，把冷启动移出首个用户请求；
- 对 10 万、20 万、50 万商品测量 `vec0` 的线性增长；只有 P95 超过预算后再引入 ANN，避免过早增加索引复杂度；
- 多请求并发场景评估连接池或只读多连接，避免单连接锁成为新的串行点。

## 8. 阶段判断

本次结果证明 SQLite + sqlite-vec 已经解决旧 JSON/Python 精确索引的主要工程性能问题，并能在 5 万商品上稳定完成真实 Qwen Challenger 检索。当前仍应保持 Challenger：缺少固定查询集、正式旧/新 A/B、质量收益、并发负载和 TP95 门禁，不能据此切换生产默认链路。
