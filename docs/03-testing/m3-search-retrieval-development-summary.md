# M3 搜索推荐检索策略与测试说明报告

> 报告日期：2026-08-22  
> 项目阶段：单实例本地 MVP，M3 主链路收口  
> 当前结论：Active 工程链路完成，但质量门禁未通过；本地默认保持 Challenger

## 1. 报告摘要

本轮开发完成了 Qwen Embedding 从非融合 Challenger 到受控 Active 的完整工程链路，包括三态开关、BM25+Qwen 并行召回、RRF 融合、TF-IDF 有界降级、来源与权重审计、固定查询集评测和开发集权重选择。

工程正确性、索引一致性、故障降级、权限复核、结果稳定性和暖态延迟均通过测试；完整自动化回归共 143 项通过。真实 5 万商品留出集测试中，BM25+Qwen 的暖态 P95 为 1.052 秒，低于 2 秒门槛，零结果率为 0，排序稳定率为 1.0。

但 Active 的 Recall@10、MRR@10 和 NDCG@10 均低于 BM25+TF-IDF 基线，总质量门禁失败。进一步扫描 Qwen RRF 权重 0.25～2.0 后，开发集仍选择等权 1.0，留出集没有改善。因此当前不能把 Active 设为默认，下一步需要解决跨品类语义误召回，而不是继续简单调权。

## 3. 本次采用的检索策略

### 3.1 总体链路

```text
用户查询
  → 意图解析与查询规范化
  → 并行召回
      ├─ catalog_search：BM25 关键词召回
      ├─ vector_search：TF-IDF 或 Qwen 语义召回
      └─ behavior_recall：仅已登录且已授权用户
  → 加权 RRF 融合与去重
  → Catalog、租户、状态、ACL 与硬约束复核
  → 商品详情与证据补全
  → 推荐结果、SSE 和 Receipt
```

离线质量评测不带 `user_id`，因此行为召回按设计跳过，只比较两条核心链路：BM25+TF-IDF 和 BM25+Qwen。

### 3.2 BM25 关键词召回

BM25 负责精确商品词、品牌词、规格词和标题词命中。它对“27 英寸 4K 显示器”“1TB NVMe 固态硬盘”等显式关键词查询尤其重要。

运行时先取展示数量约 3 倍的候选，最大 50 条，为后续融合和硬约束过滤保留冗余。BM25 原始分数只作为来源分保存在 `source_scores`，跨来源排序使用 RRF，不直接比较 BM25 与余弦相似度。

### 3.3 TF-IDF 语义基线

TF-IDF 是无模型环境下的本地语义基线，也是 Active 的故障回退源。它基于商品固定搜索文档字段构建稀疏向量并计算余弦相似度。

TF-IDF 的主要职责有两个：

1. 在 `off/challenger` 模式下作为正式语义候选；
2. 在 Active 的模型、索引或空结果异常时有界回退，保证请求仍可由 BM25+TF-IDF 完成。

### 3.4 Qwen Embedding 语义召回

Qwen 负责自然语言需求、同义表达和字面词重叠不足的语义查询。查询文本会增加商品检索任务指令，商品文档不增加指令，以保持查询侧与文档侧编码职责分离。

Qwen 查询执行流程：

```text
查询文本
  → 添加查询指令
  → 生成 1,024 维归一化向量
  → sqlite-vec 精确余弦 KNN
  → 扩大候选
  → 回到可信 Catalog 映射 Item
  → 复核租户、状态和 ACL
  → 返回正式或 Challenger 候选
```

向量索引只提供 `item_id + score`，不能成为商品事实或权限真值。向量命中必须回到当前 Catalog 取商品，并重新检查租户、状态和 ACL。

### 3.5 三种 Embedding 模式

| 模式 | 正式语义候选 | Qwen 行为 | TF-IDF 行为 |
|---|---|---|---|
| `off` | TF-IDF | 不加载、不调用 | 正常执行 |
| `challenger` | TF-IDF | 只生成对照审计，不参与 RRF | 正常执行 |
| `active` | Qwen | 正式参与 BM25+Qwen RRF | 仅故障或空结果时回退 |

Challenger 会记录 Qwen 候选 ID、分数、与 TF-IDF 的重叠数、来源版本和耗时，但不改变正式结果。Active 成功时不再重复执行 TF-IDF 全表扫描。

### 3.6 有界降级策略

Active 只对以下已知可用性问题降级：

- 模型不可用；
- 索引文件缺失或损坏；
- 模型版本、维度、Catalog 哈希或商品数不匹配；
- Qwen 返回空候选。

对应来源和错误码：

| 场景 | 实际来源 | 错误码 |
|---|---|---|
| Qwen 正常 | `qwen` | 无 |
| 模型或索引异常 | `tfidf_fallback` | `SEMANTIC_FALLBACK_TFIDF` |
| Qwen 空结果 | `tfidf_fallback` | `SEMANTIC_EMPTY_FALLBACK_TFIDF` |

程序错误不会被笼统捕获成降级，避免真实缺陷被静默掩盖。

### 3.7 RRF 融合与来源权重

每个来源先独立排序，再按以下公式融合：

```text
RRF(item) = Σ source_weight / (60 + rank)
```

默认 BM25 与 Qwen/TF-IDF 权重均为 1.0。RRF 的价值是只比较名次，不直接比较量纲完全不同的 BM25 分数和向量余弦分数。

本轮新增 `SEEKORA_QWEN_RRF_WEIGHT`，范围 `(0, 2]`。实际权重会写入工具调用 Receipt 的 `metadata.rrf_weight`。Deep Path 出现多个计划查询时，第一层先融合召回源，第二层再对各计划查询结果执行一次 RRF，避免直接比较不同查询的原始分数。

#### Qwen RRF 权重具体是什么

Qwen RRF 权重不是余弦相似度阈值，也不会修改 Qwen 模型生成的向量或 KNN 原始分数。它只控制“Qwen 排名列表在最终融合中拥有多少票”。

假设 `k=60`：

- BM25 第 1 名、权重 1.0，贡献 `1.0/(60+1)=0.01639`；
- Qwen 第 1 名、权重 1.0，同样贡献 `0.01639`；
- Qwen 第 1 名、权重 0.5，只贡献 `0.00820`；
- Qwen 第 1 名、权重 2.0，贡献 `0.03279`。

如果同一商品同时被 BM25 和 Qwen 召回，两边贡献会相加。例如某商品是 BM25 第 2 名、Qwen 第 4 名，且 Qwen 权重为 1.0：

```text
1/(60+2) + 1/(60+4)
= 0.01613 + 0.01563
= 0.03175
```

它通常会排在只被一个来源召回的商品前面。这正是 RRF 鼓励“多来源共同认可”的机制。

不同权重的含义：

| Qwen 权重 | 融合含义 | 可能收益 | 主要风险 |
|---:|---|---|---|
| 0.25 | Qwen 只有 BM25 四分之一的票 | 强化精确关键词 | 语义候选很难进入前列 |
| 0.50 | Qwen 票数减半 | 较保守地补充同义表达 | 可能损失自然语言召回 |
| 1.00 | BM25 与 Qwen 等权 | 两个来源平等参与 | 跨品类语义错误也会正常参与 |
| 1.50 | Qwen 比 BM25 多一半票 | 强化语义查询 | 放大语义误召回 |
| 2.00 | Qwen 票数是 BM25 两倍 | 近似语义优先 | 精确商品词可能被挤出 Top 10 |

这里采用的是一个全局权重：所有查询、所有商品类型都使用同一个值。它只能调整两个来源的整体影响力，不能判断“这一条 Qwen 候选是不是手机”，也不能只对某一种查询降权。因此，当错误来自候选品类本身时，全局权重只能在“丢失语义收益”和“放大语义错误”之间移动，不能从根本上修复错误候选。

### 3.8 融合后的确定性安全边界

模型候选不能绕过以下复核：

- 商品必须存在于当前 Catalog；
- `tenant_id` 必须匹配；
- 商品状态必须有效；
- 商品权限标签必须属于请求允许集合；
- 分类、价格、库存等硬约束继续由确定性约束引擎执行；
- 行为召回只能提升已经被查询源召回的商品，不能单独引入历史商品。

最终结果保存来源分、召回理由、约束通过证据、索引/Catalog 版本和降级原因，便于重放与审计。

### 4.3 质量指标

- `Recall@10`：所有已标注相关商品中，有多少出现在 Top 10；
- `MRR@10`：第一个相关商品出现得有多靠前；
- `NDCG@10`：同时考虑相关性等级和排序位置；
- 零结果率：查询是否没有任何候选；
- 排序稳定率：相同配置重复查询是否返回完全相同的商品顺序。

质量门禁要求 Active 的 Recall、MRR、NDCG 均不低于基线，零结果率不增加。

#### Recall@10：Top 10 找全了多少相关商品

Recall 关注“查全率”。对一条查询：

```text
Recall@10
= Top 10 中命中的相关商品数 / 该查询全部已标注相关商品数
```

例如人工标注认为某查询有 3 个相关商品，系统 Top 10 找到了其中 2 个：

```text
Recall@10 = 2/3 = 0.6667
```

如果 3 个都找到，则为 1.0；一个都没找到，则为 0。项目最终对所有查询的单条 Recall 做算术平均，即宏平均，避免某个拥有大量相关商品的查询完全支配总指标。

Recall 不关心相关商品在 Top 10 内的具体位置。相关商品排第 1 和第 10，对 Recall 的贡献相同。因此它适合判断召回是否遗漏，但不能单独评价排序体验。

本轮结果：

```text
BM25+TF-IDF Recall@10 = 0.851282
BM25+Qwen  Recall@10 = 0.691026
下降                    0.160256
```

这表示在当前标注口径下，Active 平均只找回约 69.1% 的相关商品，而基线能找回约 85.1%。Qwen 带来的语义候选占用了部分 Top 10 位置，使一些已标注相关商品被挤出。

Recall 的数值依赖相关性标注完整度。本项目使用双路 Top 5 候选池人工复核，适合本地 MVP 对照，但还不能代表全 Catalog 的绝对召回能力。

#### MRR@10：第一个相关结果来得有多快

MRR 是 Mean Reciprocal Rank，即“平均倒数排名”。单条查询只看第一个相关商品：

```text
RR@10 = 1 / 第一个相关商品的排名
```

如果 Top 10 没有相关商品，则为 0。示例：

| 第一个相关商品位置 | RR@10 |
|---:|---:|
| 第 1 名 | 1.0000 |
| 第 2 名 | 0.5000 |
| 第 3 名 | 0.3333 |
| 第 4 名 | 0.2500 |
| 第 10 名 | 0.1000 |
| Top 10 无相关商品 | 0 |

MRR@10 是所有查询 RR@10 的平均值。它非常重视第一条可用结果，适合衡量用户是否能快速看到至少一个相关商品。

本轮结果：

```text
BM25+TF-IDF MRR@10 = 0.938462
BM25+Qwen  MRR@10 = 0.884615
下降                 0.053846
```

两套链路的 MRR 都较高，说明大多数查询很快就能看到相关结果；但 Active 的第一个相关商品平均位置仍有所后移。MRR 只看第一个相关结果，即使后续九条全部不相关，也可能得到较高分，因此必须与 Recall 和 NDCG 一起使用。

#### NDCG@10：相关程度和排序位置是否合理

NDCG 是 Normalized Discounted Cumulative Gain，即“归一化折损累计增益”。它同时考虑：

1. 商品相关性等级，本项目使用 0、1、2、3；
2. 商品所在位置，越靠后贡献折损越大；
3. 当前结果与理想排序之间的距离。

DCG@10 的计算为：

```text
DCG@10 = Σ (2^relevance_i - 1) / log2(i + 1)
```

其中 `i` 从 1 开始表示排名。理想情况下把最高相关等级依次放在最前面，得到 `IDCG@10`：

```text
NDCG@10 = DCG@10 / IDCG@10
```

因此 NDCG 范围通常为 0～1，1 表示与理想排序一致。

例如系统前三名相关性为 `[3, 0, 2]`：

```text
DCG
= (2^3-1)/log2(2)
  + (2^0-1)/log2(3)
  + (2^2-1)/log2(4)
= 7 + 0 + 1.5
= 8.5
```

理想顺序应为 `[3, 2, 0]`：

```text
IDCG = 7 + 3/log2(3) ≈ 8.8928
NDCG ≈ 8.5/8.8928 ≈ 0.9558
```

这个例子虽然找到了两个相关商品，但 2 级相关商品被不相关商品挡在后面，因此没有得到满分。

本轮结果：

```text
BM25+TF-IDF NDCG@10 = 0.744787
BM25+Qwen  NDCG@10 = 0.667385
下降                  0.077402
```

这说明 Active 不仅遗漏了更多相关商品，已找到商品的相关性等级和位置组合也更差。跨品类但语义相似的商品进入前排，是 NDCG 下降的重要原因。

#### 为什么三个指标必须同时通过

三个指标回答不同问题：

| 指标 | 回答的问题 | 单独使用的盲点 |
|---|---|---|
| Recall@10 | 相关商品找全了吗 | 不关心 Top 10 内的顺序 |
| MRR@10 | 第一条相关结果够靠前吗 | 忽略第一条之后的全部结果 |
| NDCG@10 | 高相关商品是否整体排在前面 | 对标注等级和标注完整度敏感 |

例如，一套系统可能第 1 名总是相关，因此 MRR 很高，但剩余结果很差，Recall 和 NDCG 会揭示问题；另一套系统可能找全所有相关商品，Recall 很高，但都排在第 8～10 名，MRR 和 NDCG 会较低。

所以本项目采用联合门禁：三个指标都不能低于基线。Active 本轮三项全部下降，不能因为延迟更快或 MRR 仍然“看起来较高”就切换默认链路。

### 4.4 延迟测量

- Top K 为 10；召回源并行执行；
- 模型冷加载单独记录，不混入暖态 P50/P95；
- 首轮正式报告每条链路重复 3 轮：13×3=39 个暖态样本；
- 暖态门禁要求 Active P95 不高于 2,000 ms；
- 权重选择对底层召回做内存缓存，避免每个候选权重重复执行相同 Qwen 推理；
- 留出集最终复验仍使用真实非缓存召回。

### 5.2 功能和安全性

以下能力均通过自动化测试：

- Active 正式候选来自 Qwen；
- Challenger 结果只进入审计元数据；
- Active 成功时不执行 TF-IDF 重复扫描；
- 模型/索引异常和空结果能够回退；
- 每个候选能区分 `catalog_search/qwen/tfidf/tfidf_fallback`；
- SSE 和 Receipt 保存实际来源、版本、错误码与 RRF 权重；
- Qwen 命中不能绕过 Catalog、租户、状态、ACL 和硬约束；
- 同配置重复查询排序稳定。

### 5.3 单组件性能

| 组件 | P50 | P95 | 判定 |
|---|---:|---:|---|
| BM25 Top 30 | 759.2 ms | 864.4 ms | 可用，仍是 Python 全表扫描 |
| TF-IDF Top 30 | 427.7 ms | 510.8 ms | 可用，仍是 Python 全表扫描 |
| Qwen Query Embedding | 43.7 ms | 57.7 ms | 通过 |
| sqlite-vec KNN Top 50 | 156.2 ms | 388.7 ms | 通过本地门槛 |

### 5.4 Active 留出集的已通过指标

| 门禁项 | Active 结果 | 门槛 | 判定 |
|---|---:|---:|---|
| 查询数量 | 13 | ≥10 | 通过 |
| 暖态 P50 | 637.593 ms | 记录项 | 通过工程观察 |
| 暖态 P95 | 1,052.042 ms | ≤2,000 ms | 通过 |
| 最大暖态延迟 | 1,123.949 ms | 记录项 | 通过工程观察 |

## 6. 未通过的测试与指标

### 6.1 Active 质量门禁失败

| 指标 | BM25+TF-IDF | BM25+Qwen | 差值 | 判定 |
|---|---:|---:|---:|---|
| Recall@10 | 0.851282 | 0.691026 | -0.160256 | 失败 |
| MRR@10 | 0.938462 | 0.884615 | -0.053846 | 失败 |
| NDCG@10 | 0.744787 | 0.667385 | -0.077402 | 失败 |
| 零结果率 | 0 | 0 | 0 | 通过 |

三项排序质量指标都退化，因此即使延迟通过，总门禁仍判定失败。项目没有因为性能更快而忽略质量下降，也没有静默切换默认模式。

主要误差表现为跨品类语义相似：

- “8000mAh 长续航户外手机”会召回移动电源；
- “27 英寸 4K 设计显示器”会混入 2K 显示器或泛屏幕商品；
- “无线机械键盘办公”会混入无线薄膜键盘或有线机械键盘。

Qwen 能理解“户外、续航、办公”等语义，但当前没有在向量召回前使用确定性商品类型收窄，语义相近但品类不一致的商品会占据 Top K。

### 6.2 加权 RRF 未解决质量问题

开发集扫描结果：

| Qwen 权重 | Recall@10 | MRR@10 | NDCG@10 |
|---:|---:|---:|---:|
| 0.25 | 0.747253 | 0.833333 | 0.682061 |
| 0.50 | 0.679029 | 0.820513 | 0.652095 |
| 0.75 | 0.679029 | 0.897436 | 0.677201 |
| 1.00 | **0.777015** | 0.895604 | **0.722958** |
| 1.25 | 0.671245 | 0.895604 | 0.673361 |
| 1.50 | 0.660256 | 0.895604 | 0.668799 |
| 2.00 | 0.660256 | 0.857143 | 0.652053 |

按 NDCG、Recall、MRR 顺序选择后仍得到 1.0。降低 Qwen 权重会丢失语义候选，提高权重则会放大跨品类误召回。留出集使用选出的 1.0 后仍保持上述质量退化，因此“只调 RRF 权重”这一优化假设未通过。

### 6.3 冷启动问题未解决

模型冷加载加首查约 10.6～11.9 秒。该值没有混入暖态门禁，因此不属于本次暖态 P95 的失败项，但如果 Active 成为默认，它会明显影响进程启动后的首个用户请求。

当前尚未实现启动后受控预热。预热需要考虑：

- 不阻塞健康检查还是在 Ready 前完成；
- CUDA 显存不足时的降级；
- 多进程重复加载模型；
- 预热失败如何写入健康状态和 Receipt。

## 8. 为什么当前仍保持 Challenger

是否切换默认链路由质量与延迟共同决定：

```text
Active 可设为默认
  = 查询覆盖通过
  ∧ Recall 不退化
  ∧ MRR 不退化
  ∧ NDCG 不退化
  ∧ 零结果率不增加
  ∧ 暖态 P95 ≤ 2 秒
```

本轮只有质量条件不成立，因此最终决策是：

```text
SEEKORA_EMBEDDING_MODE=challenger
SEEKORA_QWEN_RRF_WEIGHT=1.0
```

Active 代码继续保留，用于离线评估、回归和后续改进；当前本地默认正式候选仍由 BM25+TF-IDF 提供，Qwen 只记录对照审计。

## 9. 下一步开发建议

### P0：类别感知召回

1. 扩展确定性意图解析，使手机、笔记本、台式机、显示器、键鼠、耳机、相机、平板、存储、路由器、智能穿戴和投影等查询得到标准 `product_type`；
2. 把 `product_type` 作为召回契约字段传给 BM25 和 Qwen，而不是依赖模型自行猜测；
3. Qwen 先扩大向量候选，再回到 Catalog 执行商品类型复核，避免过滤后候选不足；
4. 对无法可靠识别品类的查询保持无类别过滤，避免错误硬过滤。

### P1：独立复验

1. 类别规则只在开发集设计；
2. 保持当前 13 条留出集不参与规则调整；
3. 重新执行 Recall/MRR/NDCG、零结果率、稳定率和 P50/P95；
4. 只有全部门禁通过才修改本地默认值。

### P2：性能与冷启动

1. 评估 Ready 前预热和 Ready 后后台预热两种策略；
2. 增加真实并发阶梯测试；
3. 如果规模增长导致精确 KNN 超预算，再评估 ANN，不提前增加复杂度。
